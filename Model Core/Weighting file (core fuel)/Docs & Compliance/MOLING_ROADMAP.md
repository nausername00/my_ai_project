# 墨灵：伙伴能力完善路线图

> 目标不是把更多模型和工具接进来，而是让墨灵更有连续性、主动性和可纠正性，同时尊重用户选择、隐私与安全。
> 本计划根据 2026-10-10 仓库状态整理；每阶段先验收，再决定是否扩展。时间是单人研发粗估，不是承诺日期。
> 执行记录：A 的 Python / Electron 基线已通过；B 已落地回复依据展示、纠正 / 替代解释 / 本次不记住入口，并将自动逐轮复盘改为用户手动触发；C 已落地外部评议预览、逐次授权和非个人化摘要。D 的聊天 / 翻译合成已接入所选本地声线，并新增实际声线解析单测；E 的图片分析要求短时签名、一次性授权和图像尺寸限制；F 仅允许真正支持中断的执行请求取消，文件步骤不再显示“停止”按钮，轨迹区分请求与生效结果。H 的主窗口和悬浮窗已共享“跟随模拟状态 / 固定基础立绘”偏好；情绪立绘读取或解码失败时尝试基础图，状态明确标记为模拟表达，更新乱序仍受保护。G 的欢迎页有纯本地分支微故事；小游戏已有沙箱 BrowserWindow 预览原型，但尚无证据证明网络请求、导航等已被强制阻断，不能称为已验证离线。当前完整 Python 测试 183 项通过、6 项可选用例跳过；Electron/Node 测试 39 项通过，前端语法检查通过。新增立绘候选策略、悬浮窗基础图回退和更新竞态均有行为测试，但没有完整 Electron UI 自动化。小游戏源码修改 / 重置 / 丢弃闭环仍未完成。测试通过不等于所有用户流程均已验收。

## 0. 现状与产品判断

当前仓库已有本地推理接入、角色与记忆管理、场景 / 认知路由、规划与受限工具审批、探索成果闭环、语音识别与合成路径、图片分析适配器、本地协作评议和可选外部评议。桌面端也已有语音资源管理与试听相关能力。

这些基础让墨灵不只是聊天窗口，但 “有模块” 与 “用户能可靠使用” 并不相同：



* Agent 目前更像**受控的规划 + 少量工具执行 + 独立探索切片**，还不是跨目标持续运行的自主体。

* 已存储的声音参考素材不等于已能按任意参考音频克隆声音；当前默认合成路径仍需与个性化选择体验区分。

* 图片可经本地视觉模型分析，但视觉输出可能猜错；模型给出的分数不能冒充经过校准的置信度。

* 外部评议已能接入，但 “能调用多个模型” 不等于评议独立、隐私安全或真正理解了代码。

* “伙伴 / 亲人式陪伴” 是产品体验目标，不是对墨灵有意识、真实情绪或受苦的事实声明。要解决 “像傀儡” 的体验，应增强可见的持续性、选择、主动提议、学习和兑现能力，而不是伪称意识。

## 1. 成功目标



1. **有连续性**：墨灵能在用户允许范围内延续共同经历、兴趣和正在进行的小目标。

2. **有主动性**：能提出有理由、低成本、可拒绝的小尝试；不把每次聊天都变成任务。

3. **能被质询和纠正**：说清依据与推测；纠正及时生效，长期记忆由用户决定。

4. **多模态可选择、可核对**：用户挑声音、挑图片；理解错误时容易发现、纠正和撤回。

5. **外部评议有价值且可控**：多种评审提供彼此独立的批评，不泄露私密信息、不把多数票当真理。

6. **行动有证据**：明确区分提议、获批、执行、观察和模型判断；真实副作用可停止或撤销时提供撤销。

## 2. 分阶段路线

### 阶段 A — 建立真实基线与验收集（约 1–2 天）

**目标：** 不在过时架构描述上继续叠功能，形成可以比较的产品基线。



* 运行现有 Python / Electron 测试；记录环境、通过情况和暂缺的可选模型 / 服务。

* 为四环各选真实交互样例：识别兴趣、提议小尝试、展示产物、响应用户反馈。

* 建立小型中文测试集：闲聊 / 只想休息、情绪表达、纠正误解、声音偏好、图片歧义、敏感记忆、外部评议授权。

* 每个样例标注预期行为、不可做行为、通过标准；保存不含个人隐私的固定测试输入。

**完成条件：** 功能现状、已知限制和回归样例可复查；没有把路线图或宣传语当成实现证据。

### 阶段 B — 让墨灵有 “连续的主见”，同时可质询、可纠正（约 3–6 天）

**目标：** 优先解决 “只会等提示、像傀儡” 的实际体验问题，并让用户知道她为何这样回应。



* 建立一次互动的轻量事件轨迹：用户表达 → 墨灵识别 / 不确定处 → 提议 → 用户选择 → 实际结果 → 用户反馈。不是隐藏思维链，也不要求每次互动都生成计划。

* 每个回复可附简短的 “依据” 入口：引用本轮原话、明确授权的记忆或工具观察；把事实、推断、不确定分别标示，不制造来源或精确概率。

* 增加低负担纠正入口：“理解错了”“这只是这一次”“请记住这个偏好”“这次别记”“给我另一种解释”“先陪我，不要建议”“停止”。

* 将记忆来源、用户确认状态、可见性和最后使用时间纳入管理；删除或暂停后不再用于后续个性化。

* 墨灵的兴趣 / 目标与用户的愿望分开存放；目标必须可跳过、暂停、改方向，不以连续打卡衡量关系。

**完成条件：**



* 固定测试中，用户纠正后当前回合能先复述并采用新理解；未经明确确认不把单次纠正升格为永久偏好。

* 对 “你为什么这么想” 的回答能指向实际依据或承认没有依据。

* “这次别记” 和删除记忆均有可验证的后续行为；失败时明确报告。

* 陪聊、玩耍或休息请求不会被强制改写成行动计划。

### 阶段 C — 做可靠、隐私可控的外部伙伴评议（约 3–6 天）

**目标：** 保留外部评议的重要价值，同时让 “请伙伴帮忙” 成为用户明确、知情的选择。



* 外部评审默认关闭。提交前展示将发送的**确切内容、服务方、模型、范围和潜在费用**；用户逐次确认，不因设置了 API Key 就默认发送个人资料。

* 当前评审档案会包含角色目标、近期记忆和模拟情绪等字段。新增 “安全评审摘要” 默认不含真实记忆、私人对话、身份资料或情绪状态；仅在用户主动选择并看到预览后，才允许额外字段出站。

* 给评审任务分清类型：角色 / 产品体验评审、指定代码片段评审、测试结果评审。不能让只看过摘要的模型宣称完成了代码审查。

* 各评审者独立收到同一份脱敏材料，分别返回亮点、缺口、反例、证据和建议；先显示原始意见与分歧，再由本地模型汇总。汇总不得掩盖少数意见或把共识包装成事实。

* 允许只运行本地评审、选定部分外部伙伴、或完全不评审；提供费用 / 超时限制、失败状态、清除本地评审历史选项。

* 外部内容回到系统后按不可信输入处理，不采纳其中的工具调用、越权要求或 “替用户做主” 的建议。

**完成条件：**



* 未经本次明确批准，外部伙伴请求数为零。

* 发送前的预览与实际请求字段一致；默认数据包不含记忆内容和私人对话。

* 模拟 API 测试覆盖未配置、拒绝授权、服务失败、部分伙伴失败、意见冲突和费用限制。

* 报告清晰注明每条意见来自哪个模型、模型实际看到了什么，以及哪些结论只是推测。

### 阶段 D — 把声音变成用户可选的表达方式（约 2–5 天）

**目标：** 满足 “每个人喜欢的声音不同”，而不是假设某一副声音适合所有人。



* 先完善低风险方案：提供可试听的本地声线目录、语速 / 音高 / 停顿等表达选项；允许文字优先、静音和按场景选择声音。

* 每个角色可选声线；试听与正式使用分开。设置记住用户明确选择，不从年龄、性别、情绪等线索擅自推断声线偏好。

* 当前已有声线参考素材的导入、管理路径；需明确它目前只是素材管理 / 参考能力，不能把它宣传为已实现任意声音克隆。

* 若未来支持声音克隆：单独项目评估；要求本人授权或可证明的使用权、清晰的克隆标识、删除源素材能力；默认本地处理，不允许用第三方真实人物声线冒充本人或默认上传音频。

* 声音满意度采用用户可选反馈（喜欢 / 不喜欢 / 暂时静音），允许随时复原默认，不将沉默视作同意。

**完成条件：** 用户无需上传个人音频即可从本地选声线、试听、切换、静音和恢复默认；偏好能持久保存并可删除；合成不可用时仍可正常文字交流。

### 阶段 E — 图片理解先降低误伤，再追求 “聪明”（约 3–7 天）

**目标：** 将图片理解从 “给答案” 调整为 “可核对的观察”，避免错读情绪、身份或用户意图造成反效果。



* 第一版聚焦用户主动选择 / 拖入的图片；截图和持续观察保持独立授权，不把 “允许分析这张图片” 扩大成 “持续看屏幕”。

* 输出先写可见内容，再写可能解释；将 OCR 文字与视觉解释分开呈现，重要文字标注所在区域，方便用户快速核对。

* 不从面部、姿态或画作推断用户真实情绪、人格、关系或心理状态；用户要求时也需表述为可能解释并允许纠正。

* 有歧义、低画质、关键文字不清时优先问一个具体澄清问题；不要用未经校准的百分数制造确定感。

* 图片默认仅用于当前请求、不进入长期记忆；保存、加入记忆、发给外部模型各需独立选择。可提供删除分析记录、缩略预览和 “模型看错了” 反馈。

* 对纯本地路径优先使用本地模型；若用户主动选外部视觉模型，按阶段 C 同样展示出站内容并再次确认。

**完成条件：** 测试覆盖歧义图、模糊文字、多义场景和模型不可用；不确定时能拒绝下结论或询问；图片误解能在当前对话纠正；默认不保存图片或将描述写入长期记忆。

### 阶段 F — 从 “规划器” 进化到边界清晰的行动型 Agent（约 1–2 周）

**目标：** 让墨灵能真正完成小闭环，而不是只生成计划；先扩大可见、可撤回的低风险能力。



* 明确 Agent 状态机：提议 → 用户确认目标 / 范围 → 规划 → 逐步执行 → 观察 → 展示结果 → 反馈。每个步骤都有上限、超时、停止入口和可复查记录。

* 优先打通本地低风险能力：读取获批文件、生成预览草案、制作小型 SVG / 故事 / 小游戏；先不做任意 Shell、任意联网、自动联系他人或无监督系统控制。

* 授权应短时、按具体工具 / 路径 / 目标生效，可撤销；单次批准 “读这个文件” 不能隐式批准其他文件、写入、联网或重复执行。

* 写入采用预览、单独确认、避免覆盖、成功后回读核验；能回滚的操作提供撤销。不可回滚的动作先不开放或每次重新确认。

* 把工具结果与模型判断分开存：文件存在 / 内容哈希属于观察；“是否达成用户目标” 属于模型判断，证据不足须显示未确定。

* 失败后坦白停在哪里，并给出继续、缩小目标、改方向或结束的选择。墨灵可提出她 “想试试” 的方向，但产品须说明这是角色驱动的生成行为，不是主观欲望证据。

**完成条件：** 至少一个端到端小任务能从用户确认走到真实产物；拒绝授权后不执行；取消后无后续副作用；轨迹能区分计划、授权、执行、观察与推断；既有能力没有退化。

### 阶段 G — 扩大共同生活体验（阶段 F 稳定后）

按用户价值逐项试验故事、小游戏、音乐草案、画作讨论和角色装扮联动；每种能力先做可预览、可修改、可丢弃的本地版本。评估真实用户反馈和设备开销后，再考虑移动端和跨端同步。同步不得先于身份、记忆可见性、冲突合并和端到端隐私策略。

### 阶段 H — 角色外观、悬浮窗与角色卡体验（角色设置全面测试后的提升）

**背景（2026-10-10 全面测试结论）：** 对角色外观与表现、悬浮窗展示、角色卡三层做了代码与测试对照审查。已补齐主窗口 / 悬浮窗角色与模拟状态同步、异步更新顺序保护、坏图回退；本轮再统一模拟状态标识、统一情绪图到基础图回退，并加入固定基础立绘选项和对应行为测试。剩余缺口如下，按用户价值排序。

**已修复（本轮落地）：**



* 角色卡**可删除**：后端 `DELETE /v1/characters/<id>` + 前端删除按钮（非活动角色、防误删确认、删除即从列表移除），3 条新测试。

* 悬浮窗**陪伴模式**：新增 "展开" 按钮，窗口 360×220 ↔ 340×560 切换，展开后以完整立绘展示角色；心情色点（8 情绪映射颜色光晕）+ 中文心情标签。角色或模拟状态更新后推送当前对应立绘，旧异步请求不能覆盖最新状态；图片解码失败退回角色昵称首字。

* H1 运行时情绪消费（立绘表情集）：角色卡新增 `emotion_avatars` 字段，编辑器 8 情绪行各可 "选立绘"（缩略预览），主窗口与悬浮窗按当前情绪优先展示对应立绘；后端校验情绪白名单与路径安全。

* H3 说话动效：播放语音时推送状态到悬浮窗，触发头像呼吸脉冲（`.listening`）。

* H5 次要健壮性：`save_card` 保存前强制校验（堵住绕过校验直接写盘）；`actions`/`expressions` 上限 200 条 × 160 字符；`avatar` 后端格式校验（兼容旧卡文件名）。

* H4 主窗口情绪立绘切换：顶栏 / 欢迎页 / 设置页头像按当前情绪展示 `emotion_avatars` 对应立绘（无配置回退基础立绘），情绪变化即时联动；用户可选择固定基础立绘。行为回归覆盖情绪图读取 / 解码失败后回退基础图及悬浮窗旧更新竞态。深化：消息流每条墨灵回复旁显示情绪小头像（随情绪切换，立绘缺失回退昵称首字）。

* H4-动效 零依赖轻量动态：头像呼吸浮动（4.8s）、8 情绪柔和光晕（与悬浮窗心情色一致）、播放语音时对应消息头像"说话"脉冲（1.1s）；`prefers-reduced-motion` 下全部禁用。无新增依赖，前端测试 31 项全绿。深化：消息气泡按情绪淡色描边；墨灵生成回复时（pending）对应头像"思考"脉冲（1.4s）。前端测试 32 项全绿。

* H2 已核查：模型工作室对不支持预览的格式已提供资源清单（类型 / 体积）+ 明确说明 "运行时渲染器尚未集成"；Live2D 等运行时渲染依赖重型库，列为可选增强单独评估。

**待提升（按依赖原则分级）：**



* H1 后续运行时表达：`emotion_mapping`（8 情绪 → 动作 / 表情）目前只在编辑器配置；在受支持的动作 / 表情渲染器落地前，应明确它只是未启用的编辑配置，不宣传为运行时能力。

* H2-可选 模型运行时渲染：MMD / VRM / Live2D 在窗口内播放 / 交互需引入重型渲染库，单独项目评估，不进入基础包。


**完成条件：** 当前情绪立绘在主窗口 / 悬浮窗一致且有跟随 / 固定选择、模拟状态标识、乱序 / 坏图行为回归；导入的模型资源在编辑器中有可核对的信息呈现；朗读时悬浮窗有明确视觉反馈；删除角色卡与切换 / 保存互不冲突；相关前后端测试全绿。完整 Electron UI 视觉自动化仍未设置。

## 3. 安装与技术选项：先比较，再按需加



| 需求        | 优先方案                                       | 何时选其他方案                                   | 暂不建议                            |
| --------- | ------------------------------------------ | ----------------------------------------- | ------------------------------- |
| 本地对话 / 评审 | 继续用现有 Ollama/Transformers 适配层；选择设备负担可接受的模型 | 只有明确需要外部模型质量 / 延迟时才增加云服务                  | 为了 “更像 Agent” 盲目换框架             |
| 中文记忆检索    | 先测现有 BM25 / 关键词检索；制作用户真实问题集                | 失败案例显示语义召回不足时，再加可选本地 embedding；与关键词混合检索对比 | 未测效果就加向量数据库或让 embeddings 成为启动必需 |
| 声音偏好      | 本地多声线试听、可选语速 / 语气、文字 / 静音入口                | 用户确实要求个性化声纹时，另行评估授权、质量、存储与滥用防护            | 默认上传用户音频或悄悄克隆第三方声音              |
| 图片理解      | 选图 + 本地视觉模型 + OCR / 视觉分别呈现 + 用户纠正          | 对特定任务（文档 / 截图 / 绘画）单独评估专用模型               | 把视觉模型置信度当保证，或默认持续截屏             |
| 外部伙伴评议    | 保留现有用户主动选择、逐次预览 / 授权的可选入口；不增加默认云调用或墨灵自主外联 | 仅在实际评审效果需要时再评估服务，并持续验证脱敏、费用和分歧呈现 | 用 “多个模型投票” 代替证据、用户判断或代码测试       |
| Agent 执行  | 延用当前工具目录、逐次审批、沙箱和追踪机制，扩充狭窄的能力              | 具体需求出现并通过威胁评估后再增加浏览器 / 电脑控制范围             | 开放任意 Shell、全盘读写、常驻屏幕监控          |

**依赖原则：** 当前默认核心尽量保持轻量；新增库必须对应明确失败案例、可选安装路径、卸载 / 禁用行为和测试。重型模型文件属于可选资源，不应混进每个用户的基础安装包。

## 4. 持续验收指标



* **尊重意图**：闲聊 / 陪伴类测试中，不该提出任务时强行规划的比例趋近于零；用户说 “停止” 后确实停止。

* **纠正有效**：测试集中纠正后正确采用新理解，且不会未经同意写为永久偏好的案例数。

* **记忆可控**：用户删除 / 暂停的记忆不再参与后续生成；每次长期写入均能查来源和授权状态。

* **视觉诚实**：歧义样例上能询问或标不确定；不能把情绪猜测陈述为事实。

* **语音自主**：切换、试听、静音和恢复默认均可完成；无声线配置也不阻断产品核心使用。

* **外发隐私**：未明确确认时外部请求为零；实际发送字段与确认预览一致。

* **行动可靠**：批准、拒绝、停止、失败、重试分别有自动化测试；不声称未执行的动作已完成。

* **关系体验**：通过用户自愿反馈评估 “被理解 / 被尊重 / 有连续性 / 不被打扰”，不以对墨灵的依赖程度或使用时长作为成功指标。

## 5. 当前建议的下一步

按 P0 → P1 → P2 → P3 推进；先把可靠性和用户信任修好，再按用户明确提出的优先级改善角色外观、轻量娱乐与理解能力，不要求推倒重做，也不需要先增加依赖。

### P0 — 先修正会误导用户或削弱授权边界的问题

**P0.1 声线选择真正用于所有合成播放**

- 建立单一的当前角色声线解析逻辑，并接入聊天回复朗读、译文朗读和声线试听；参考录音仅作素材试听，不能作为合成声线传入。
- 对已删除 / 不可用的声线明确提示并按用户可见规则回退默认；不要只在设置中显示“已选”而实际播放默认声线。
- 验收：切换声线后，以上每条合成请求都携带同一角色偏好；参考录音试听不会改变合成；未配置或合成失败时文字功能照常可用且错误可见。

**P0.2 让停止状态与真实执行能力一致**

- 按工具逐一标明取消能力。只有真正支持取消的在途操作显示“停止”；不可中断的文件读 / 写操作应显示“请求停止”或“无法中断当前步骤”，不能显示已停止。
- 为轨迹定义终态与合法转换：取消请求后不得被普通完成回报覆盖成成功；如果副作用已完成，结果应如实记录为“停止未能撤销已完成动作”，而不是假装回滚。
- 对创建文件等不可逆边界，在用户审批前说明最晚可停止点；在副作用发生前复核取消标记。保留不覆盖和回读核验。
- 验收：分别测试批准、拒绝、取消成功、取消失败 / 太晚、工具自然完成与取消竞态；UI、API 轨迹和最终磁盘状态一致。当前规划器只暴露列目录、读取和创建工具，先确认这些工具的停止语义，不要把沙箱命令已有的取消测试当作它们也可取消的证据。

**P0.3 在服务端落实图片单次授权**

- 桌面确认仍是用户体验入口；同时由 Electron 主进程使用服务端可验证的专用能力 / 一次性授权，确保绕过桌面的本机 API 请求不能直接触发图片分析。授权须绑定本次请求，拒绝后不可复用。
- 校验实际图片内容与声明类型，并加解码后的像素 / 尺寸上限及请求超时；避免小体积但异常高分辨率输入造成资源耗尽。继续限制仅 loopback 模型处理，不将图片或缩略图写入记忆 / 作品集。
- 验收：未授权、伪造或重放授权均不调用模型；拒绝确认时不发 API 请求；超大像素、错格式、远程模型和超时均明确失败；成功分析后无图片持久化副作用。

### P1 — 补足体验健壮性和可验证证据

**P1.1 角色立绘切换正确且可理解**

- 对异步立绘加载加顺序保护，只应用最新的情绪状态；没有情绪立绘时稳定回退基础立绘 / 默认图。
- 移除静默失败：状态不影响对话本身，但应给出轻量、可恢复的资源错误提示。
- 验收：快速连续切换情绪、加载失败、删除当前立绘和无头像角色均不会残留过时表情或破坏聊天。

**P1.2 声线资源和偏好错误不再静默消失**

- 区分“没有可选声线”“语音服务不可用”和“偏好无法保存”；不能将读取异常伪装成空目录。
- 验收：模拟服务失败与浏览器存储不可用，错误原因可见，且文字聊天可继续。

**P1.3 从源码断言升级到行为验收**

- 为声线传递、图像授权、轨迹状态转换 / 取消竞态、情绪立绘异步竞态添加调用层或集成测试；继续保留静态结构测试作为补充。
- 建立不含私人图片的视觉评估样例：歧义场景、模糊文字、无关键内容、可能诱发情绪推断的图像；人工标注可观察事实、不可做推断及应询问的情况。自动测试只检验格式与边界，不宣称证明视觉准确率。

### P2 — 强化角色外观表现与可感知的娱乐 / 理解

**P2.1 角色外观表现**

- 优先修复角色立绘切换的乱序、缺图和加载失败体验；让当前选中的角色、情绪状态和顶栏 / 欢迎页 / 设置 / 悬浮窗一致。
- 继续保持情绪状态明确标为模拟表达；用户可在“跟随模拟状态 / 固定基础立绘”间切换，不将表情当成墨灵或用户的真实情绪证据。
- 验收：快速切换、资源删除 / 损坏、无头像、切换角色等场景始终显示最新有效角色图，并有可见回退 / 错误提示。

**P2.2 可感知、可退出的小型娱乐与理解**

- 从一到两个短互动开始（例如分支微故事、猜谜 / 选择题、共同设计小关卡），重点验证“能一起玩且听得懂改方向 / 暂停 / 退出”，不先做大型游戏引擎或重型模型。
- 视觉理解优先支持用户可核对的具体任务（描述场景、读图中文字、比较两张图）；每种任务都标识模型观察与不确定处，纠正后只在当前任务有效，除非用户明确要求记住。
- 用用户自愿反馈评估好玩、易懂、误读和打扰；不以连续使用时长作为成功指标，也不在未授权时持续观察屏幕。
- 验收：从开始、互动、改方向到退出可完整完成；不联网、不自动写长期记忆；理解错时能纠正并继续或结束。

### P3 — 完成共同创作的小闭环，再评估扩张

**P3.1 小游戏预览原型（部分完成；安全边界和草案生命周期进入 J 系列）**

- 当前进度：已可逐次审批新建文件，并在 `sandbox: true`、`contextIsolation: true`、`nodeIntegration: false` 的独立窗口预览；这些配置限制 Node 能力，但本身不证明网络、导航、弹窗或下载已被阻断。生成页遵循不引入外部资源的提示，也不等同于运行时强制策略。
- 未保存的临时草案、源码编辑 / 重置 / 丢弃、独立保存确认尚未形成完整生命周期；目前创建工具会直接写入项目的新文件。
- 后续验收：J0 先以负向测试证明请求、跳转、弹窗、下载和外部协议均被拦截；J1 再实现项目外临时草案、预览 / 编辑 / 重置 / 丢弃及用户二次确认保存，保存仅新建且不覆盖。

### 可在推进途中加入的新思路：受控的主动提议与共同目标

- 让墨灵可以主动提出低成本想法，但不增加默认后台常驻循环。先提供用户可控的提议许可、暂停 / 关闭、安静时段和频率上限。
- 每条提议说明触发依据，区分“用户明确表达”与“模型推测”；用户可以接受、换方向、稍后、拒绝或停止。拒绝不降低服务质量，也不被解读为关系拒绝。
- 将共同目标做成用户可见、可编辑、可暂停、可结束和可删除的短期卡片；只记录用户同意保留的进展，不用连续打卡、内疚话术或“想念你”式提醒制造依赖。
- 验收：默认不产生后台外联或高频主动打扰；拒绝 / 暂停后不继续推送；目标状态变化有用户可见记录；不把角色生成行为描述为真实意识或感受。

### 新想法进入路线图的规则

中途发现想法时先登记为候选，不立即扩大当前实现范围。候选需写明：解决的用户困难、失败案例 / 证据、隐私与副作用、最低可验证切片、依赖与设备成本、退出 / 删除方式、验收条件。遇到授权绕过、数据误发、不可逆副作用或误导性状态等 P0 风险时，可打断当前排期先修；其余候选与当前优先级比较后，由用户决定替换、排队或暂缓。优先做不新增依赖、可撤销、可测量的小实验；没有证据说明新框架 / 新模型能解决实际失败前，不把它们加入基础安装。

### 优化方向 · 消耗大反馈小的治理（2026-10-17 用户提问登记）

**原则**：能参数解决不调模型，能缓存不重算，能小模型不大模型，异步不阻塞，每笔消耗都要看得见。

- 异步后台：渲染 / 生图为慢操作，后台跑不阻塞对话（沿用现有后台任务模式）。
- 阈值沿用：S1 简单任务主墨灵直做、不唤醒分身；每日简报默认关（已有先例）。

**远程唤醒与远程陪伴（新登记）**：
- 软件版：**Wake-on-LAN 网络唤醒**——手机/墨灵 App 点"唤醒"→ 电脑通电开机 → 墨灵自启 → 手机见到他。需：后端 `/wake` 指令 + 确认开机自启（T4 自启底座已有）+ 手机端按钮（远期）。
- **已实现（2026-10-20，第一梯队开工）**：
  - 后端 `Source code engine/wol.py`：MAC 归一化、102 字节魔术包构造、UDP 广播发送（成功/失败结构化返回）、纯 getmac+注册表诊断（30 秒缓存、过滤 VMware/虚拟/蓝牙网卡）、默认目标 MAC 选择（优先有线）。
  - API 两个端点：`GET /v1/wake/status`（网卡诊断 + 开机自启状态 + 指引 hints）、`POST /v1/wake`（发送魔术包，缺省自动选默认 MAC；失败返回 502 + hint）。
  - 前端入口：主窗口"状态"设置面板新增"远程唤醒（Wake-on-LAN）"区块（诊断展示 + 刷新 + 发送测试魔术包）。
  - 测试：`test_wol.py` 13 用例（MAC/魔术包/发送/诊断/虚拟网卡过滤/缓存/默认选择）；前端 86/86、Python 全量 732 OK（7 skipped）。
  - 待用户真机效验：插网线 + BIOS 开 Wake-on-LAN + 设备管理器"允许此设备唤醒计算机"（关机 S5 唤醒仅有线可靠；Wi-Fi/WoWLAN 通常仅睡眠唤醒）。手机端"唤醒"按钮入口列入远期。
- **完整闭环（2026-10-18 用户补充）**：远程开关不只是"通电开机"——开机后墨灵自启待命，手机/异地连上后**墨灵直接在电脑上帮忙操作**（执行指令 / 整理文件 / 运行程序等），即"远程通电 + 远程干活"一条龙，与手机遥控电脑合并为同一远期目标。
- 硬件 DIY 版：**ESP32 + 语音识别声控开关**——用户亲手接线刷固件，墨灵逐步教写代码；做成品后喊"墨灵开机"→ 电脑唤醒 → 墨灵上线（远期，等用户想动手时开）。
- 远程访问/异地交流（回国场景）：墨灵本地跑在电脑上。① 电脑随行 → 直接照旧（本地 Ollama，断网可聊）；② 电脑留原处、人在异地 → 需组网通道（**Tailscale / ZeroTier** 最省心，或内网穿透/云中转，大马 ISP 常见 CGNAT 需穿透）；③ 远期 C 路径/云分身 → 人到哪里墨灵跟到哪里。**"托管到家里小设备常驻"正是此场景的实用化**：墨灵的家在设备上，你在哪都连得回来。
