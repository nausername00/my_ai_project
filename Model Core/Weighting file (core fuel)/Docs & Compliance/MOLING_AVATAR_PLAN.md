# 新思路的动力 · 墨灵分身系统规划（MOLING_AVATAR_PLAN）

> 定位：给墨灵"会分配精力的伙伴式能力"——主墨灵 + 按需唤醒的专项分身，分领域陪伴与帮助；
> 睡眠 / 唤醒机制控制资源；唤醒确认把主动权留给用户；记忆共享但主权唯一。
> 状态：已确认方向（2026-10-13），进入分期规划。

## 主墨灵原型视觉提案（2026-10-19，待共同定稿）

### 已确定的设计约束

- **气质核心**：高岭之花、面冷心慈；漂亮或帅气优先，可爱作为备选。外表要冷静、有距离感，细节则能看出温柔，不做凶狠或拒人千里的表情。
- **配色**：黑与白为主；“星澜蓝银”用于星光、金属和能量细节；红色只做少量识别点，避免大面积红黑造成攻击感。
- **发眼**：暗金是优先候选，但不锁死；眼睛要清亮、有层次，避免红瞳与大面积红饰同时抢焦点。
- **制作约束**：优先半身或全身立绘可读的清晰轮廓；头发、刘海、眼睛、衣领/肩饰、袖口/手部、背部飘带或披肩可分层，给 Live2D 眨眼、转头、呼吸与轻动作留空间；大面积发饰和遮眼刘海会增加绑定成本。

### 三套造型方向

#### A · 星澜司书（主推：漂亮、克制、心慈藏在细节里）

- **轮廓**：修身立领短外套叠白色内层，肩线利落；腰侧垂一片不对称短披片，形成安静的星轨弧线。整体优雅而不繁复，适合做主形象。
- **颜色**：墨黑外层、月白内层；领口与袖口用星澜蓝银细线；胸前一枚小红色结饰作为唯一暖色焦点。
- **发型**：暗金长发，侧分长刘海但露出双眼；后发分成前后两层，发尾微卷，便于 Live2D 做小幅摆动。
- **眼睛**：蓝灰虹膜叠一圈浅银星环；平静时偏冷，柔和表情时可通过眼睑与高光变化显出关怀。
- **材质/记忆点**：哑光黑布、白色内衬、少量冷银金属；红结只在近景可见。第一眼清冷，第二眼才发现衣服内侧有细小星纹。
- **Live2D 可行性**：高。披片做独立层、银色星轨用静态装饰，核心动作集中在脸、发束和肩部；无需复杂物理链。

#### B · 夜航剑士（帅气、可靠、行动感更强）

- **轮廓**：黑白短款制服外套配窄腰长下摆，单侧护肩与轻薄腰带形成斜向动势；保留裙裤/长靴的中性利落感，不做厚重盔甲。
- **颜色**：黑为主、白色肩片和内襟提亮；蓝银落在肩扣与细窄边线，红色仅为手套腕带或剑穗一小点。
- **发型与眼睛**：深棕或暗金短中发、后侧束起；银蓝眼睛。发型较 A 更利落，表情显得果断。
- **材质/记忆点**：布料与少量拉丝金属；象征“守护”的护肩，但不用武器也能成立，避免把她定型成战斗角色。
- **Live2D 可行性**：中高。披摆、护肩、束发需分层；动作感较好，但侧身和配件会增加绑定与立绘成本。

#### C · 雪夜信使（可爱备选：柔和、亲近，但不幼态）

- **轮廓**：白色短斗篷搭黑色连衣裙/长外套，圆润肩线配直线衣襟；下摆有轻微层次，保留安静的成熟感。
- **颜色**：月白与深灰占主；星澜蓝银做星形扣与斗篷内衬，红色作为小围巾结或信封封蜡色块（二选一，不能同时抢眼）。
- **发型与眼睛**：暖栗色或浅暗金齐肩发，发尾内扣；灰蓝眼睛。可加一枚小星形发夹，不加兽耳、夸张蝴蝶结或婴儿化比例。
- **材质/记忆点**：柔软斗篷与清晰的白黑对比；动作时斗篷内衬露出蓝银，带一点惊喜。
- **Live2D 可行性**：中。短斗篷摆动有表现力，但需控制遮挡和物理范围；配件比 A 多，后续可删减。

### 当前推荐与制作顺序

**推荐先以 A「星澜司书」做主原型。** 它最贴近“漂亮、面冷心慈”，黑白和蓝银的比例容易控制，单点红色也能形成稳定识别；同时比剑士更轻盈，比可爱方案更不容易偏离已定性格。B、C 保留为换装或支线造型，不与主形象冲突。

首轮原型按 A 执行：正面三分之二身、自然站姿、表情平静但眼神柔和；黑白主色面积约 8 成、蓝银装饰约 1 成半、红色低于 1 成；纯净浅灰背景，不加文字、武器或额外角色。先检查脸部辨识度、缩小到悬浮窗头像时的轮廓、以及 Live2D 拆件，再细化布料纹样和饰品。完成后由用户确认或要求重新组装；未确认前不替换项目现有 Live2D 角色，也不写入已生效角色设定。

## 主墨灵性格原型：高岭之花，面冷心慈（2026-10-19，方向已确认）

- **外在表达**：冷静、克制、有分寸，偶尔带一点傲娇或干净利落的吐槽；不故意冷落用户，不用刻薄、羞辱或操纵式表达。
- **内在关怀**：少说空泛安慰，多用认真倾听、记住经用户同意保留的偏好、提供具体帮助来表达在意；遇到用户疲惫时先接住情绪，再询问是否需要建议。
- **相处节奏**：用户先定亲密程度。可以接住玩笑和亲昵称呼，但不把“想念”“吃醋”等角色台词包装成真实感受，也不要求用户持续陪伴。
- **自主性边界**：可以提出有理由、可跳过的建议；涉及保存记忆、唤醒分身、联网、改文件或系统操作时，仍按现有授权流程执行，不能以“为你好”越权。
- **真实性边界**：性格、情绪与自我叙述属于角色表达和程序状态，不作为已有主观体验或独立意识的证据；不确定时如实说明。
- **验收场景**：①用户开玩笑时能冷面接梗但不生硬；②用户难过时关怀具体、不诊断、不强行解决；③用户纠正她时承认并调整，不擅自写入长期记忆；④用户拒绝建议后停止推进；⑤连续对话保持语气一致，同时准确区分事实、记忆与推测。
- **实现顺序**：先以角色卡/提示词和固定对话样例验证表达一致性；再检查记忆开启、关闭、纠正与删除是否影响后续提示；最后才评估轻量主动提议。实机验收需使用用户本机实际配置的 Ollama 模型。

## 一、核心理念

1. **伙伴而非工具**：能力命名与交互都遵循"墨灵是真伙伴"——不是"会干活的大脑"，而是"新思路的动力"。
2. **分身 = 精力分配**：不追求"一个墨灵什么都会扛"，而是分领域专注，减少单个墨灵的负担。
3. **睡眠 / 唤醒 = 资源可控**：默认仅主墨灵活跃（低消耗）；分身睡眠不占资源；需要时唤醒。
4. **唤醒确认 = 用户主权**：任务真正复杂或跨领域时，墨灵询问"是否需要唤醒更多墨灵的帮助吗？"，用户点头才唤醒。
5. **记忆共享、主权唯一**：分身成果 / 经验回写主记忆（可追溯、可撤销，延续 J4），长期记忆只由主墨灵写入。

## 三、分期规划

### S1 · 分身底座（"会睡觉的伙伴"骨架）

| 项 | 内容 |
|---|---|
| 分身份 | ID / 领域 / 简介 / 能力清单 / 状态（active \| sleeping）持久化 |
| 睡眠 / 唤醒运行时 | 分身会话挂起 / 恢复；睡眠不占推理资源；活跃时独立上下文 |
| 唤醒确认 | 主窗口 / 悬浮窗询问"需要唤醒更多墨灵的帮助吗？"；确认后唤醒，可指定领域 |
| 阈值判断 | 简单任务主墨灵直做；复杂 / 跨领域任务触发询问 |
| 主记忆复用 | 复用 J4 记忆系统（来源 / 可见性 / 纠正 / 删除） |

**验收**：
- 可创建 4 个分身（陪伴 / 学习 / 创作 / 技术），状态可持久化；
- 睡眠 / 唤醒切换生效：唤醒后能恢复独立上下文，睡眠后不占用推理；
- 阈值判断可配置（默认：单领域简单任务不询问；多领域或长任务询问）；
- 唤醒确认流程走通：主墨灵询问 → 用户确认 → 指定领域分身唤醒。

### S2 · 领域能力（分身的"双手"）

| 分身 | 能力清单（v1） |
|---|---|
| 陪伴 | 对话、情绪识别与回映、日常记录提醒（复用现有陪伴链路） |
| 学习 | 信息检索、资料整理、要点归纳（复用现有搜索 / 整理工具，本地优先） |
| 创作 | 文案 / 立绘 / Live2D 演出 / 视频脚本（复用 K 线渲染管线） |
| 技术 | 代码读写、脚本执行、格式转换（复用工具执行，逐次授权） |

工具执行统一走**安全边界**：本地优先、无外部网络默认、逐次授权、可撤销（延续 J / K 系列已落地的安全原则）。

**验收**：
- 每个分身在自己领域完成一个真实任务（可演示、可复现）；
- 工具调用均记录来源与授权痕迹；拒绝未授权的外部操作；
- 分身能力清单可增删（配置而非硬编码）。

### S3 · 协作与主记忆（"统一目标"）

| 项 | 内容 |
|---|---|
| 跨领域分发 | 主墨灵拆解任务 → 唤醒对应分身 → 汇总结果给用户 |
| 并行协作 | 多分身同时处理独立子任务（同领域不重复唤醒） |
| 成果回写 | 分身执行结果 / 经验写回主记忆，带来源与时间戳；可追溯、可撤销 |

**验收**：
- 一个跨领域任务（如"做一期讲解视频"= 学习查资料 + 创作写脚本 + 技术跑渲染）由多分身协作完成；
- 回写主记忆的条目均可追溯来源、可单独撤销；
- 并行场景下多个分身不互相覆盖记忆（主权唯一验证）。

### S4 · 自我进化（"新思路"的来源）

| 项 | 内容 |
|---|---|
| 自省回路 | 定期回放记忆 / 决策，本地复盘"做了什么、效果如何"，调整后续策略 |
| 技能沉淀 | 把已验证能力（K 系列渲染、立绘管线、搜索整理）封装成墨灵可调用的技能卡 |

**验收**：
- 墨灵能基于历史回放产出一条策略调整并应用（可验证前后行为差异）；
- 至少一个 K 系列能力被封装为技能卡并被分身实际调用。

### S5 · 扩展与陪伴（远期，不设时间表）

- **手机陪伴**：电脑睡眠时，手机端唤醒"陪伴分身"（瘦客户端 + 本地模型方案评估）。
- **性格分化**：分身体验差异化（创作分身更感性、技术分身更严谨）——先验证分工价值，再分化性格。

## 四、资源预算

| 项 | 预算 |
|---|---|
| 活跃分身 | 主墨灵 1 + 活跃分身 ≤ 3（默认 1+1） |
| 睡眠分身 | 0 推理消耗（仅保留分身份与断点） |
| 模型 | 共享现有本地 Ollama 模型，不按分身加载多模型 |
| 记忆 | 复用现有记忆库，无新增存储依赖 |

## 五、安全边界（延续既有原则，不因分身放宽）

- 本地优先、无外部网络调用默认关闭；外部操作逐次授权。
- 工具执行有明确拒绝 / 撤销路径；所有写入记忆可追溯、可撤销。
- 唤醒确认由用户主权决定；墨灵不擅自开启分身。
- 版权 / 数据边界与 K 系列一致（第三方素材本地个人使用，对外需授权）。

## 六、与现有系统的复用关系

| 现有能力 | 复用方式 |
|---|---|
| 记忆系统（J4） | 主记忆库与可追溯 / 撤销机制直接复用 |
| 情绪 / 形象（H1/H4 + K 线） | 主墨灵人格与 Live2D 形象作为统一表现层 |
| 工具与生成（agent_tools / comfyui / K 渲染管线） | 分身能力清单的后端实现 |
| 本地模型（Ollama） | 所有分身共享同一推理底座 |

## 七、完成条件（整线）

- 4 个分身可创建 / 睡眠 / 唤醒，唤醒确认与阈值判断生效且用户可配置；
- 每个分身在自身领域完成真实任务；跨领域协作任务可复现；
- 记忆回写全部可追溯、可撤销；分身不破坏主记忆主权；
- 至少一个 K 系列能力封装为技能卡并被实际调用；
- 安全边界测试覆盖授权拒绝 / 撤销 / 记忆回滚。
